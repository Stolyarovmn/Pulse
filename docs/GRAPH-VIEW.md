# GRAPH-VIEW: пайп расследования и два вспомогательных вида

Что рисуем, когда оператор выбрал сущность и хочет увидеть цепочку вокруг
неё.

Главный вид — **пайп расследования**: выбрал процесс, вправо раскрылись
факты о нём (откуда запущен, какой порт, какой контейнер, его лог,
системный лог про него, его проблемы). Это не топологический граф:
расследование линейно, а факты — листья. Отсюда и определение «красиво»:
фиксированные колонки, выровненные значения, ноль пересечений
по построению.

Два других вида отделены сознательно, потому что у них другая природа
рёбер и другая раскладка:

| Вид | Природа | Состояние |
|---|---|---|
| **A. Пайп расследования** (главный) | сущность → её факты; глубина 2, пересечений нет | **реализовано**: `pulse-tui/src/pipe.rs`, экран `screens/pipe.rs`, клавиша `g` |
| **B. Дерево подпроцессов** (по требованию) | процесс → процесс, у процесса ≤ 1 родитель, значит чистое дерево | **нужно ребро**: `ppid` разбирается (`pulse-collect/src/parse.rs:201`, `:240`), но в связь не превращается — `process.rs:280` ставит только `RunsIn` (процесс → cgroup) |
| **C. Граф владения** (самый дорогой) | `RunsIn`, `OwnedBy`, `MemberOf`, `BackedBy` плюс будущие `ListensOn`, `ConnectsTo` (`pulse-core/src/relation.rs:10-26`) | настоящий DAG с fan-in: 200 процессов → одна cgroup → один unit, поэтому нужна слоистая раскладка |

Смешивать их в один «универсальный рендерер» нельзя: дерево провалится
на fan-in владения, а DAG-механика избыточна там, где оператору нужна
цепочка фактов.

## 0. Состояние: виды A и A2 работают

Оба вида собраны и сняты с живого агента (`tmux`, 120 колонок,
непривилегированный запуск). Клавиши: `g` — открыть пайп, `↑↓←→` — движение
курсора по осям сетки, `⎵` (пробел) — раскрыть или свернуть ветку,
`v` — древо или отступы, `Esc` — выход, `q` — выход из программы.

**Оси, а не список.** Курсор двигается в тех же координатах, что кадр:
`↓` идёт в тот же столбец следующего ряда, `→` — в соседний бокс. Раньше
движение было линейным по перечню из двенадцати категорий, а кадр — сеткой
из трёх колонок, поэтому «вниз» визуально уводило вправо; раскрытие висело
на `→` и спорило с движением. Число колонок сообщает кадр
(`PipeState::columns_for`), поэтому в узком виде отступами оси работают
по одноколоночной сетке.

**Стиль рамок** повторяет панели omp: скруглённые углы `╭╮╰╯`, подпись
вписана в верхнюю границу (`╭─── files ▸ ───╮`), фокус выделен тяжёлой
рамкой `┏━┓`, а не двойной. Ряд боксов висит на стволе слева
(`├─`, `╰─`) и соединён ветвью по верхней границе: без связей это была
сетка плиток, из которой не видно, что все факты принадлежат одной
сущности.

Пайп с отступами на собственном процессе агента:

## 1. Вид A: пайп расследования

```
ENTITIES                                  PIPE ─ nginx: worker   pid 851
 nginx.service        unit+14p  ◉ 38%      ├─ exe      /usr/sbin/nginx
 ├ web-frontend       ctr       ◉ 31%      │  user     www-data uid 33
 ├ nginx: master 812  proc      ○  2%      │  cwd      /
 └ nginx: worker 851  proc ◂    ◉ 14%      ├─ ports    tcp 0.0.0.0:80
 pg-main              ctr       ◉ 22%      │           tcp6 [::]:80
                                           ├─ owner    ctr web-frontend
                                           │           unit nginx.service
                                           ├─ limits   mem 512M/1G thr 12%
                                           ├─ files    8 из 214 дескрипторов
                                           │           /var/log/nginx/access.log
                                           ├─ log      12:41:07 GET /api 500
                                           ├─ journal  нет в этой сборке
                                           └─ problems memory.pressure crit
```

Правила:

- **левая панель — существующий список сущностей, правая — пайп фокуса.**
  `Tab` переключает панели, как сейчас;
- **`→` раскрывает ветку, `←` сворачивает.** На экране Entities эти
  клавиши свободны; на Timeline `←→` остаётся скрабом времени — конфликт
  разрешается по экрану, а не новой клавишей;
- **`Enter` идёт по ветке `owner`** — то есть пайп и есть расследование:
  спуск и подъём подчиняются уже принятому правилу уровней
  (`pulse-tui/src/investigate.rs:28`, `drill_steps:106`, `side_steps:216`);
- **категории фиксированы и упорядочены по полезности**, а не по
  структуре данных: сначала «кто это», потом «чем занят», потом «что
  о нём пишут»;
- **колонка категории фиксированной ширины**, значения выровнены по левому
  краю — это и даёт аккуратный кадр без трассировки линий.

### Состав веток и откуда берутся данные

| Ветка | Содержимое | Источник |
|---|---|---|
| `exe` | исполняемый файл | `ProcessDetails.exe` (`pulse-core/src/details.rs:49`) |
| `user` | владелец, uid | `.user`, `.uid` (`details.rs:47-48`) |
| `cwd` | рабочий каталог | `.cwd` (`details.rs:50`) |
| `cmdline` | команда с аргументами | **под выключателем** `security.read_cmdline` (`pulse-core/src/config.rs:59`); выключен — ветка так и говорит |
| `ports` | слушающие сокеты: протокол, адрес, порт | `.ports: Vec<Port>` (`details.rs:56`, тип `Port` — `details.rs:20-26`) |
| `owner` | контейнер, unit, pod вверх по владению | граф: `parent` и связи владения; распознавание владельца — `pulse-collect/src/cgroup.rs` |
| `limits` | лимит и текущая память cgroup, доля троттлинга | `CG_MEM_CURRENT`, `CG_MEM_LIMIT`, `CG_CPU_THROTTLE_RATIO` (`metric.rs:99-101`, `:98`) |
| `files` | открытые файлы и сколько всего дескрипторов | `.files`, `.fd_total` (`details.rs:52-54`), обычные файлы отличаются `OpenFile::is_regular` (`details.rs:39`) |
| `log` | хвост того файла, который процесс держит открытым | решение 5 в `docs/SOLUTIONS.md`: чтение по требованию, без хранения |
| `journal` | системный журнал про этот unit за окно | решение 5; **до его реализации ветка честно говорит, что источника нет** |
| `problems` | открытые проблемы сущности с evidence | `Problem` (`pulse-core/src/problem.rs:87`), сборка — `pulse-engine/src/analyzer.rs:127` |
| `resources` | диск и интерфейс, которыми пользуется | связи `BackedBy`, список — `investigate::context_resources:179` |

### Три свойства, без которых пайп не имеет смысла

1. **Ленивость.** Ветка читает данные только при раскрытии. Это не
   оптимизация, а уже принятый принцип: обход `/proc/<pid>/fd` для двух
   тысяч процессов — десятки тысяч syscall на такт, и агент сам
   становится проблемой (комментарий `details.rs:11-14`). Кэш на снимок
   уже есть — `DetailsCache` (`details.rs:92`).
2. **Честность вместо тишины.** У деталей есть отдельное поле
   `restricted` (`details.rs:62`) именно потому, что пустой список
   читался бы как «файлов и портов нет». В пайпе это значение ветки:
   `files  restricted: нет прав на fd чужого пользователя`.
3. **Свёртка по месту.** `files` показывает несколько строк и остаток
   числом («8 из 214»), `ports` — все, потому что их единицы. Первыми
   сворачиваются ветки без проблем и без нагрузки — та же логика, что
   в логической свёртке `pulse-tui/src/fold.rs`.

### Деградация по ширине

Ширина эскиза выше посчитана, а не оценена: **80 колонок** ровно.

| Ширина | Что показываем |
|---|---|
| ≥ 100 | список сущностей и пайп рядом, значения не переносятся |
| 80–99 | список и пайп рядом, длинные значения переносятся с отступом под колонку |
| 60–79 | пайп на весь экран, список скрывается (возврат по `Tab`) |
| < 60 | пайп вертикально: категория строкой, значение под ней |

Обрезка значения посередине токена запрещена: путь или порт, обрезанный
в середине, читается как другой путь или другой порт.

## 1а. Вид A2: граф-режим (боксы) — `g`

То же содержимое, что в пайпе, но узлами-боксами в ярусах. Включается
клавишей `g` из того же экрана; данные, ленивость и правила честности
общие с видом A — меняется только раскладка.

Кадр ниже собран в реальной символьной сетке и замерен, а не нарисован
от руки: бокс 22 колонки (18 под значение), три бокса в ряду, ярус
переносится на следующий ряд, если ветвей больше трёх.

```
┌ exe ───────────────┐  ┌ user ──────────────┐  ┌ cwd ───────────────┐
│ /usr/sbin/nginx    │  │ www-data uid 33    │  │ /                  │
└────────────────────┘  └────────────────────┘  └────────────────────┘
         │                       │                       │
┌ ports ─────────────┐  ┌ owner ─────────────┐  ┌ limits ────────────┐
│ tcp 0.0.0.0:80     │  │ ctr web-frontend   │  │ mem 512M/1G        │
│ tcp6 [::]:80       │  │ unit nginx.service │  │ thr 12%            │
└────────────────────┘  └────────────────────┘  └────────────────────┘
┌ files ─────────────┐  ┌ resources ▸ ───────┐  ┌ journal ▸ ─────────┐
│ 8 of 214 fds       │  └────────────────────┘  └────────────────────┘
│ /var/…/access.log  │
└────────────────────┘
┌ log ───────────────┐  ┌ problems ──────────┐  ┌ chain ▸ ───────────┐
│ 12:41:07 GET /api  │  │ memory.pressure    │  └────────────────────┘
│ 500                │  │ crit  since 12:39  │
└────────────────────┘  └────────────────────┘
```

### Анатомия бокса и ленивость

- **Свёрнутый бокс — две строки**: заголовок с `▸` и нижняя рамка.
  Значений в нём нет, и **чтения источника не происходит вовсе**
  (`resources ▸`, `journal ▸`, `chain ▸` в кадре выше).
- **Раскрытый бокс** — заголовок, значения, рамка. Раскрытие делает одно
  чтение на процесс и складывает результат в кэш снимка
  (`DetailsCache`, `pulse-core/src/details.rs:92`); повторное свёртывание
  и раскрытие в пределах одного снимка чтений не добавляет.
- **Ширина бокса фиксирована**, поэтому раскрытие меняет только высоту:
  кадр растёт вниз и никогда не прыгает по горизонтали. Это условие
  читаемости, а не косметика — иначе после каждого `→` глаз теряет место.
- **Длинное значение переносится внутри бокса**, а путь сокращается
  по сегментам: `/var/log/nginx/access.log` → `/var/…/access.log`.
  Обрезка посередине токена запрещена: обрезанный путь читается как
  другой путь.

### Измеренные требования к месту

| Величина | Значение |
|---|---|
| панель пайпа | **70 колонок** |
| кадр целиком с панелью сущностей (30) | **100 колонок** |
| высота: ряды боксов 16 + фокус 3 + шина 2 + легенда 2 | **23 строки** плюс подвал |

Отсюда лестница деградации: **≥100 колонок и ≥25 строк** — граф-режим;
**80–99** — пайп с отступами (вид A, 80 колонок); **60–79** — пайп без
панели сущностей; **<60** — вертикальный пайп. Переключение
автоматическое, с подписью, какой вид показан: молча подменять
раскладку нельзя.

### Иконки и легенда

- Иконки категорий (шестерёнка, человек, папка, щит, датчик) допустимы
  только как надстройка над способностями терминала: в Unicode-режиме
  глиф, в ASCII-режиме — ничего, а не `?`. Место для такой таблицы уже
  есть — `struct Glyphs` (`pulse-tui/src/theme.rs:54`).
- Легенда обязана использовать словарь модели, а не свой. Классов
  состояния восемь: `Inactive`, `Normal`, `Active`, `Saturated`,
  `Degraded`, `Warning`, `Critical`, `Failed`
  (`pulse-tui/src/state.rs:26-43`). Пятисловная легенда вида
  «ok / warn / info / crit / unknown» вводит второй словарь состояний
  и противоречит принципу единого authoritative-состояния: либо
  показываем восемь, либо документируем группировку восьми в пять
  и используем её везде одинаково.

### Приёмка граф-режима

- **ноль чтений до раскрытия**: тест на фикстуре считает обращения
  к источнику деталей — у кадра со свёрнутыми боксами их нет;
- **раскрытие меняет только высоту**: тест сравнивает горизонтальные
  позиции боксов до и после `→` — они равны;
- **ни одно значение не обрезано посередине токена**: путь сокращается
  по сегментам, длинная строка переносится;
- **кадр укладывается в 100×25** на фикстуре из этого документа,
  и при 99 колонках вид автоматически меняется на пайп с подписью;
- **ASCII-режим**: рамки из `+ - |`, иконок нет, не-ASCII символов
  в кадре ноль;
- **значение никогда не растягивает рамку**: превышение внутренней
  ширины переносится на следующую строку, правая граница всех боксов
  ряда совпадает по колонке (этот дефект уже был получен на макете:
  значение в 20 символов при внутренней ширине 18 разъехало рамку);
- **замер иконок не выполняется там, где его нельзя выполнять**: в не-TTY
  (тесты, CI, `pulse top`) и при `ui.ascii` иконки выключены без запроса
  к терминалу; результат замера кэшируется на сессию, в кадре запросов
  нет;
- **глиф с шириной, отличной от единицы, выключает набор целиком**:
  фикстура с двухклеточным глифом даёт кадр без иконок, а не кадр
  со сдвинутой рамкой;
- **включение и выключение иконок не меняет раскладку**: иконка стоит
  только в строке заголовка, ширина бокса и переносы значений совпадают
  в обоих режимах (тест сравнивает кадры);
- **детерминизм**: две сборки кадра на одном снимке побайтово равны.

### Что из макета воспроизводимо буквально, а что нет

Механизм уровней уже есть: `Capability { TrueColor, Ansi256, Ascii }`
с автоопределением по `COLORTERM` и `TERM`
(`pulse-tui/src/theme.rs:18-49`), а таблица глифов под уровень —
`Glyphs::for_capability` (`theme.rs:65-85`). Новые глифы графа кладутся
туда же, а не рассыпаются по экранам.

**Воспроизводится точно:**

| Элемент макета | Чем рисуется |
|---|---|
| рамки блоков | `┌ ┐ └ ┘ ─ │`, скруглённые `╭ ╮ ╰ ╯`; в ASCII — `+ - \|` |
| цветные блоки | фон и цвет ячейки, `bg()` уже используется (`theme.rs:138`) |
| цвет по состоянию | палитра классов состояния, восемь классов (`state.rs:26-43`) |
| пунктирные связи | `╌ ╍ ┄ ┅`; в ASCII — `-` |
| точки стыка связей | `● ○ ◆ ◇`; в ASCII — `o` |
| выделение фокуса | двойная рамка `╔ ═ ║` плюс яркий цвет |
| рамка проблемы | толстая рамка `┏ ━ ┃` плюс красный цвет и маркер `◆` |
| маркер раскрытия | `▸` и `▾` (в наборе глифов уже есть `selected: "▸"`) |

**Иконки: определяется на старте, но не всё.** Разделить надо два разных
вопроса, потому что у них разный ответ.

**Ширина глифа измеряется достоверно.** В зависимостях есть crossterm
(`Cargo.toml:33`), а значит доступен запрос позиции курсора: напечатать
глиф до первого кадра, прочитать позицию (`crossterm::cursor::position`),
вычесть — получить фактическую ширину 0, 1 или 2. Это ловит ровно тот
случай, который ломает сетку: двойная и неоднозначная ширина. Замер
делается один раз за сессию и кэшируется: он требует записи в терминал
и чтения ответа, поэтому в кадре ему места нет.

**Наличие глифа в шрифте измерить нельзя.** Приложение общается
с эмулятором терминала, а не со шрифтом: имя шрифта портируемо не
сообщается, а отсутствующий глиф обычно всё равно занимает одну ячейку —
замер скажет «ширина 1», а на экране будет пустой прямоугольник.
Гадать по `TERM_PROGRAM` бессмысленно: Nerd Font ставится независимо
от эмулятора.

**Набор выбирается настройкой `ui.icons`** рядом с `ui.ascii`
(`pulse-core/src/config.rs`) и действует на **весь интерфейс**, а не только
на пайп. Три значения:

| Значение | Что рисует | Когда |
|---|---|---|
| `off` (по умолчанию) | ничего | кадр обязан быть читаемым на любом шрифте из коробки |
| `nerd` | **глифы Nerd Font** из диапазона Font Awesome (`U+F000…U+F2FF`) | установлен патченный шрифт |
| `unicode` | символы блока геометрических фигур `U+25xx` | патченного шрифта нет, но иконки хочется |

`icons = true` принимается как синоним `unicode` — так значение уже успело
попасть в конфигурации, и ломать чужой файл из-за переименования нельзя.

**Словарь один на весь интерфейс** — `crates/pulse-tui/src/icons.rs`, тип
`Icon`. Две таблицы символов неизбежно разошлись бы: часть экранов получила
бы глифы, часть осталась без них, и опереться на форму символа стало бы
нельзя. Словарь покрывает 32 смысла: двенадцать категорий фактов пайпа,
восемь видов сущностей (хост, unit, cgroup, процесс, контейнер, pod, диск,
интерфейс), семь экранов и режимов (обзор, проблемы, сущности, время,
поиск, команды, справка), режим наблюдения, пауза и три уровня серьёзности.

Инварианты набора закреплены тестами в том же модуле:

- `nerd_set_is_complete_and_private_use` — у каждого смысла есть глиф, и это
  один символ приватной области `U+E000…U+F8FF`; иначе «включил nerd» тихо
  рисовало бы обычные символы.
- `geometric_set_is_complete_and_single_width` — запасной набор целиком
  лежит в блоке `U+25xx`. Ограничение блоком и есть гарантия одинарной
  ширины: символ из другого блока может оказаться двойным и разъехать рамки.
- `glyphs_are_distinct_within_each_set` — символы внутри набора
  не повторяются. Ровно эта жалоба и открыла работу над иконками:
  одинаковый символ у всех категорий делает набор бесполезным.
- `off_set_is_empty_everywhere` — при `off` кадр совпадает с кадром сборки
  без иконок вообще.

- Иконка занимает ровно две колонки перед подписью категории, и ширина
  колонки считается вместе с ней: включение набора **не сдвигает значения**
  (проверяется тестом `icons_do_not_shift_values`).
- В ASCII-режиме (`ui.ascii = true`, `TERM=dumb`) иконок нет ни в одном
  наборе: там гарантированы только ASCII-символы.
- Каждая категория имеет глиф в обоих наборах, и в наборе `nerd` это
  обязательно символ приватной области `U+E000…U+F8FF` — иначе «включил
  nerd» тихо рисовало бы обычные символы (тест
  `nerd_set_covers_every_branch_with_private_use_glyphs`).

### Что поставить для набора `nerd`

1. **Шрифт.** Патченный шрифт Nerd Fonts, обязательно вариант с суффиксом
   `Mono` — он одинарной ширины: `JetBrainsMono Nerd Font Mono`,
   `FiraCode Nerd Font Mono`, `Hack Nerd Font Mono`. Вариант без `Mono`
   рисует часть глифов двойной ширины и разъезжает рамки.
   Установка на Windows: `winget install DEVCOM.JetBrainsMonoNerdFont`.
2. **Терминал.** Шрифт задаётся эмулятором, а не WSL: Windows Terminal →
   профиль → Appearance → Font face. Внутри WSL ставить шрифт не нужно.
3. **Цвет.** Для полной палитры терминал должен объявлять
   `COLORTERM=truecolor` (Windows Terminal делает это сам); иначе Pulse
   переходит на 256 цветов, а при `TERM=dumb` — на ASCII.
4. **Включение.** `ui.icons = "nerd"`. Если вместо иконок появились пустые
   прямоугольники — шрифт не патченный или выбран не `Mono`-вариант;
   до установки шрифта работает `ui.icons = "unicode"`.

**Не воспроизводится:** свечение и ореол вокруг блоков (синий у фокуса,
красный у проблемы на макете), градиенты, сглаживание, тени, скругления
вне символьной сетки. В терминале нет подпиксельной графики: у ячейки
есть только символ, цвет текста и цвет фона. Замена уже названа выше —
двойная и толстая рамка плюс цвет; это читается как акцент, но
не притворяется свечением.

**Цена рамок, названная числом.** То же содержимое в виде отступов
укладывается в 80 колонок, боксами — в 100: рамки стоят 20 колонок
и по две строки на узел. Поэтому граф-режим — отдельный режим по `g`,
а не новый вид по умолчанию: текущий язык интерфейса сознательно
обходится линиями разделов (`Borders::TOP`, `screens/mod.rs:187-188`),
чтобы не платить шириной за рамки на каждом экране.

## 2. Вид B: дерево подпроцессов

Предварительное условие: ребро процесс → процесс. `ppid` уже разбирается
(`parse.rs:201`), но связи нет, поэтому сегодня дерево строить не из чего.
Ставится там же, где сейчас `RunsIn` (`pulse-collect/src/process.rs:279-281`);
родитель ищется по pid в том же такте, при отсутствии родителя процесс
остаётся на cgroup, как сейчас.

Раскладка тривиальна и потому надёжна: у процесса не больше одного
родителя, значит это чистое дерево — отступ на уровень, `├─`, `└─`, `│`,
свёртка тяжёлых ветвей через `fold.rs`, пересечений не бывает
по построению.

Включение — переключением вида на экране Entities (там же, где `m`
переключает логический и технический вид), а не отдельным экраном:
оператор остаётся в том же списке.

## 3. Вид C: граф владения (слоистый)

Нужен, когда вопрос не «что известно про этот процесс», а «как связаны
многие»: 200 процессов в одной cgroup, cgroup на диске, unit в pod.
Здесь неизбежен fan-in и пересечения, поэтому раскладка слоистая.

1. **Слой = уровень модели**, вычислять не нужно: `investigate::Level`
   уже упорядочен от общего к частному (`investigate.rs:660-663`).
   Ресурсы — крайний правый слой, они листья.
2. **Порядок внутри слоя** — две-три итерации барицентра, тайбрейк
   по имени обязателен, иначе кадр перестаёт быть воспроизводимым.
3. **Трассировка только ортогональная**: вертикальный канал между
   слоями, затем горизонтальный подвод. Диагоналей сетка знаков не даёт.
4. **Пересечение показывается честно** глифом `╫` (ASCII `#`): спрятанное
   пересечение читается как отсутствие связи.
5. **Стиль ребра — тип связи**, а не украшение:

   | Связь | Unicode | ASCII |
   |---|---|---|
   | владение (`ParentOf`, `OwnedBy`) | `───▸` | `--->` |
   | исполнение (`RunsIn`, `MemberOf`) | `╌╌╌▸` | `..>` |
   | ресурс (`BackedBy`) | `┄┄┄▸` | `~~>` |
   | сокет (`ListensOn`, `ConnectsTo`) | `═══▸` | `==>` |

6. **Соединители**: `─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼ ╫`, в ASCII `- | + #`;
   разрешение стыков — таблицей, а не «последний победил».

Бюджет: не больше 60 узлов на кадр (дальше свёртка), не больше шести
слоёв (столько уровней в модели). При нехватке ширины вид C сменяется
видом A — деградация видом, а не тишиной.

## 4. Что чем кодируется во всех видах

- **масса узла** — нагрузка (принцип глифа состояния уже принят),
  класс состояния — цветом существующей палитры;
- **проблемные сущности** — маркер и первыми в порядке: внимание идёт
  к проблеме, а не к геометрии;
- **фокус** — маркер `◂` и яркая строка, остальное dim;
- **числа** — в формате строки vitals (`pulse-tui/src/screens/mod.rs:380`),
  чтобы одна и та же величина везде выглядела одинаково.

## 6. Приёмка

- **ленивость**: тест на фикстуре считает обращения к источнику деталей —
  до раскрытия ветки их ноль, после раскрытия одно на процесс;
- **детерминизм**: две сборки кадра на одном снимке побайтово равны
  (образец — тест равенства двух сборок глифа, `glyph.rs:644-647`);
- **честность**: при `restricted` ветка показывает причину; при
  отсутствии источника журнала ветка говорит об этом, и тест это
  проверяет;
- **свёртка**: процесс с 214 дескрипторами даёт несколько строк и остаток
  числом, а не 214 строк;
- **ширина**: при 60 колонках список скрывается, при 50 — пайп встаёт
  вертикально; ни одно значение не обрезано посередине токена;
- **ASCII**: в ASCII-режиме в кадре нет ни одного не-ASCII символа;
- **вид C**: на фикстуре с перекрёстными связями тест ожидает точное
  число пересечений, рост ловится как регресс.

## 7. Порядок работ

1. **Вид A, ветки, которые уже обеспечены данными**: `exe`, `user`,
   `cwd`, `ports`, `files`, `owner`, `limits`, `problems`, `resources`.
   Ничего собирать не нужно — только раскладка и ленивое раскрытие.
2. **Ветки `log` и `journal`** — после решения 5 из `docs/SOLUTIONS.md`
   (чтение хвоста по требованию, без хранения).
3. **Вид B** — после ребра из `ppid`.
4. **Вид C** — слоистая раскладка.
5. **Socket-рёбра в виде C** — после сущности `Socket` (решение 1):
   тогда `ListensOn` и `ConnectsTo` перестают быть заготовкой.

## 8. Что сознательно не делается

- силовые и радиальные раскладки: непредсказуемый кадр, нетестируемо;
- диагональные и кривые линии: сетка знаков их не даёт;
- анимация графа: принята только фаза кадра глифа
  (`docs/SOLUTIONS.md` 6.3);
- рендер всех процессов хоста разом без свёртки: нечитаемо и дорого;
- «универсальный» рендерер на все три вида: у них разная природа рёбер.
