# SCENARIOS

Двенадцать сценариев расследования в Pulse TUI. Клавиши — фактический keymap
(`pulse-tui/src/screens/help.rs`, spec v0.9 §180–181):

`1–4` — экраны (Overview / Problems / Entities / Timeline);
`↑↓` или `k j` — строка; `Enter` — открыть выбранное видимое;
`Esc` — назад / закрыть Inspector или overlay; `Tab`/`Shift+Tab` — панель;
`/` — поиск; `:` — палитра команд; `?`/`F1` — help; `q`/`Ctrl+C` — выход;
`m` — logical/technical view (Entities); `s` — сортировка; `f` — фильтр типа;
`←→` — scrub по времени; `+/−` — зум окна; `F` — к LIVE; `A`/`B` — метки
сравнения; `D` — semantic A/B diff; `p` — пауза отображения;
`: raw events` и `: story` — режимы Timeline.

Каждый сценарий: симптом → действия в Pulse → на что смотреть →
интерпретация и ограничения v1.

---

## 1. CPU 100% — кто виноват?

**Симптом.** Глиф состояния на Overview перешёл в насыщенный класс (CPU-сектор
заполнен), строка SIGNALS показывает высокий CPU%.

**Действия.**
1. `1` — Overview: строка SIGNALS (`CPU …`), блок `RELEVANT LOGICAL ENTITIES`
   — таблица `NAME CPU MEM S [WHY]`: строчки с причиной ранжирования.
2. `Enter` — по выбранной строке: расследование спускается по уровню
   (сервис/контейнер → cgroup → процесс); `Esc` — точный возврат.
3. В Inspector: SUMMARY (CPU/MEM сущности), PROBLEMS и EVIDENCE (метрика,
   порог, значение), CHAIN/RELATED (списки навигации, `Tab` переключает).
4. В процесс (терминальный уровень): USER, EXEC, CWD, слушающие порты,
   открытые файлы — по требованию.
5. `2` — Problems: `psi.cpu` (warn 0.20, crit 0.50, clear 0.10) подтверждает
   давление; EVIDENCE показывает, на какой сущности порог сработал.
6. `4` — Timeline: lane `CPU` и Incident Story — когда началось;
   `A`/`B` + `D` — сравнить «до» и «после».

**Интерпретация.** `RELEVANT` показывает, кто потребляет CPU, а не только
сколько: причина у каждой строки. Троттлинг контейнера — отдельная проблема
`saturated cgroup` (сценарий 4).

## 2. Диск полон (fs 94%)

**Симптом.** В vitals Overview строка `… DISK … / 94%` (заполненность корня
по формуле `df`), цвет по `theme.ratio`; если худший значимый mount заметно
полнее корня (>+1%), добавляется `worst fs <n>%`.

**Действия.**
1. `1` — Overview: зафиксировать `/ <n>%` и `worst fs` в SIGNALS.
2. `Enter` на хост (Inspector): SUMMARY — total/free/available; PROBLEMS.
3. `2` — Problems: ждать срабатывания `psi.io` (warn 0.10 / crit 0.30) или
   `disk.latency` (warn 20 ms / crit 50 ms, гейт `has_disk_traffic`).
4. `4` — Timeline + `: story`: когда заполненность начала расти;
   `A`/`B` + `D` — diff двух моментов (новые сущности, изменения метрик).
5. Выход за пределы TUI: `host_filesystem_root_utilization/total_bytes/
   free_bytes`, `host_filesystem_worst_utilization` в `/metrics`
   (или `pulse serve`).

**Ограничение v1 — честно.** В `default_rules()` **нет fill-правила**:
94% сама по себе проблему не порождает. Проблема fires только при давлении:
`psi.io`/`disk.latency`. Диск, заполненный 100%, но не нагруженный по IO,
проблемы не создаст — это зафиксированный разрыв v1 (см. FEATURES.md,
«Честные разрывы»). Детали по mount (какой, какой fstype) наружу не
выходят — только корень и худшая значимая.

## 3. Load average растёт

**Симптом.** Внешние инструменты (uptime, мониторинг) показывают рост
load average; в TUI оператор видит CPU% и PSI.

**Действия.**
1. `1` — Overview: SIGNALS — CPU% и `PSI MEM`, `IO WAIT`; глиф (масса =
   худшая известная доля: psi ×8, iowait ×4).
2. `2` — Problems: `psi.cpu` (0.20/0.50) — это более точный индикатор
   «ядро не успевает», чем loadavg: PSI считает долю времени, проведённую
   задачами в ожидании, а load average считает и uninterruptible sleep (D) —
   записи в медленный диск раздувают его без CPU-нагрузки.
3. `3` — Entities, `f` — фильтр по типу, `s` — сортировка: найти сущности
   с высоким IO (связь «load растёт, а CPU пустой» → ищите дисковый блок).
4. `4` — Timeline: lane `IO` (PSI io full avg10) — корреляция с ростом load.

**Ограничение v1 — честно.** Метрики `host_load1/5/15` собираются
(`/proc/loadavg`), зарегистрированы в реестре (id 8/9/10, сырые значения
без нормализации на ядра) и публикуются в `/metrics`, но **в TUI их строки
нет**: ни в vitals, ни в lanes Timeline. Оператор TUI работает с CPU/PSI,
loadavg доступен через `pulse serve` / `pulse top`.

## 4. Контейнер троттлится

**Симптом.** Сервис в контейнере периодически «замирает» при пике;
CPU-квота исчерпана.

**Действия.**
1. `2` — Problems: `saturated cgroup` — правило `cgroup.throttle`
   (warn 0.10 / crit 0.25, clear 0.05) по `CG_CPU_THROTTLE_RATIO`;
   гейт `has_cpu_quota` — правило молчит, если квоты нет.
2. `Enter` — на сущность cgroup/контейнер: имя логического объекта
   (от главного процесса, ID хранится рядом), EVIDENCE — доля троттлинга
   против порога.
3. `3` — Entities, `m` — technical view: иерархия cgroup → контейнер →
   процессы (`RunsIn`/`MemberOf`), чтобы видеть, какой процесс создаёт пик.
4. `4` — Timeline + `: story`: периодичность троттлинга, совпадение с
   нагрузкой.

**Интерпретация.** Троттлинг — это «квота < спрос», а не «медленный хост»:
EVIDENCE показывает долю затроченного времени, а `psi.cpu` хоста может быть
спокойной. Лечение — квота или реплика, а не ядро.

## 5. OOM-убийство

**Симптом.** Процесс/контейнер внезапно исчезает; ядро убило его по памяти.

**Действия.**
1. `2` — Problems: `memory.oom` — OomRule: **любое ненулевое приращение
   OOM-счётчика → критично** (окно 60 c); порогом не гасится, это событие.
2. `4` — Timeline, `: story` (Incident Story): OOM-событие как значимое
   изменение; вокруг него — последние переходы состояний.
3. `3` — Entities: исчезнувший процесс больше нет в графе (мёртвые записи
   вытесняются последними по политике потолка памяти); `f` — фильтры,
   чтобы найти выживших соседей по контейнеру.
4. `A`/`B` + `D` — diff «до/после»: кто ушёл, как изменилась память.
5. `2` — параллельно `memory.pressure` (0.85/0.95) и `swap.pressure`:
   предвестники — давление на память и swap часто читаются до самого убийства.

**Интерпретация.** OOM — терминальный вердикт ядра; Pulse показывает его как
событие (crit), а не как плавный порог, и связывает с давлением памяти,
которое ему предшествовало.

## 6. Сеть: кто шлёт трафик?

**Симптом.** В vitals Overview строка `NET <rx/tx>` (стрелки направления;
в ASCII-режиме — метки RX/TX) показывает рост пропускной способности.

**Действия.**
1. `1` — Overview: зафиксировать `NET` в SIGNALS; блок RELEVANT — сущности,
   чьи изменения объясняют рост.
2. `3` — Entities: `f` — фильтр по типу (сеть/контейнер/процесс),
   `s` — сортировка по сетевым метрикам сущности.
3. `Enter` — на процесс: терминальный уровень — **слушающие TCP/UDP-порты**
   из `/proc/net`, исполняемый файл, пользователь; это ответ «кто именно».
4. `4` — Timeline: момент начала роста; `D` — diff.

**Ограничение v1 — честно.** Правил по сети в `default_rules()` нет
(ни warn, ни crit) — сетевой трафик виден как метрика, но сам по себе
проблему не порождает. Если рост сети сопровождается задержками, fires
`psi.io` или `disk.latency` только при дисковом давлении. «Кто шлёт»
в v1 — вопрос расследования (порты процесса), а не автоматическая проблема.

## 7. Порт занят: кто его держит

**Симптом.** Контейнер или сервис не стартует: `bind: address already in
use`, `port is already allocated`.

**Действия.**
1. `3` — Entities: `/` — поиск по имени сервиса или контейнера (`Enter`
   применяет фильтр, заголовок показывает активный фильтр); `f` — фильтр
   по типу, если имя неизвестно.
2. `m` — logical/technical view: в логическом виде сервис свёрнут
   (`unit+14p`), в техническом видны все его процессы.
3. `Enter` — спуск до процесса; терминальный уровень даёт **слушающие
   TCP/UDP-порты** из `/proc/net`, исполняемый файл, пользователя, рабочий
   каталог. Это и есть ответ «кто держит порт».
4. Если процесс чужой и прав нет — экран говорит `restricted`, а не молчит:
   значит порт держит процесс другого пользователя.
5. `4` — Timeline `: story`: когда владелец порта появился. Если это
   перезапуск, видно, что старый процесс не умер.

**Интерпретация.** Порт в v1 — факт процесса, а не сущность графа: идти
нужно от процесса к порту. Обратного индекса «порт → владелец» нет.

**Ограничение v1 — честно.** Сущность `Socket` — открытый вопрос
(`IDEAS.md`, `docs/ROADMAP.md` 3.6); правил на порты нет, поэтому проблема
сама не возникнет; без прав детали чужого процесса — `restricted`.

## 8. Сервис не запускается

**Симптом.** systemd или docker сообщает о неудачном старте, а в Pulse
проблема не появилась.

**Честный ответ сразу.** Pulse не читает состояние systemd unit
(`active`/`failed`) и не читает журналы: упавший сервис для Pulse —
отсутствующая сущность. На «почему сервис сам не стартовал» (конфигурация,
зависимости, права) Pulse не отвечает. Он отвечает на «что происходило
на хосте в этот момент» и «убило ли сервис ядро».

**Действия.**
1. `2` — Problems: внешние причины смерти старта — `memory.oom` (OomRule:
   любое ненулевое приращение убийств за окно 60 c → crit),
   `memory.pressure` (`MEM_UTIL` 0.85/0.95), `swap.pressure` (0.25/0.60),
   `fd.pressure` (`FD_UTIL` 0.80/0.95 — исчерпание дескрипторов),
   `cgroup.throttle` (0.10/0.25, гейт `has_cpu_quota`).
2. `3` — Entities: `/` — поиск по имени. Сущность есть — процесс жив,
   значит падает не старт, а работа; сущности нет — процесс не дожил
   до такта сбора.
3. `Enter` на unit или контейнер → CHILDREN: сколько процессов внутри
   осталось.
4. `4` — Timeline `: story`: появление и исчезновение сущностей вокруг
   попытки старта; `A`/`B` + `D` — что изменилось между «до» и «после».
5. Терминальный уровень процесса: открытые файлы — какие журналы держал
   сервис (`/var/log/...`). Это указание, где читать причину вне Pulse.

**Ограничение v1 — честно.** Нет коллектора состояния unit
(`docs/ROADMAP.md` 3.5); нет чтения journald (3.7); процесс, умерший
быстрее одного такта (по умолчанию 1 c), в графе не появится вовсе.

## 9. Нет сети или нет интернета

**Симптом.** Соединения не устанавливаются; строка `NET` в vitals около
нуля или трафик резко упал.

**Честный ответ сразу.** Pulse — наблюдатель, а не пробник: ping, DNS
и TCP-проверок он не делает. Отличить «нет линка», «нет маршрута»
и «недоступен внешний адрес» он не может. Он показывает то, что видят
счётчики хоста.

**Действия.**
1. `1` — Overview: `NET <rx/tx>` в vitals — host-агрегат пропускной
   способности. Нуль по обоим направлениям при живых процессах — признак
   проблемы уровня хоста, а не приложения.
2. `3` — Entities: `f` — фильтр по типу, выбрать интерфейс (сущность
   NetIf); `Enter` — метрики интерфейса: rx/tx bytes, packets, **errors**,
   **drops**, throughput (реестр 70..=79, `pulse-collect/src/net.rs`).
   Рост errors и drops — деградация интерфейса; нули по packets при живом
   линке — трафик не идёт.
3. `2` — Problems: сетевых проблем не будет — правил по сети
   в `default_rules()` нет. Появятся соседние, если сеть встала из-за
   нагрузки: `psi.io`, `psi.cpu`.
4. `Enter` на процесс: слушающие порты — подтверждение, что приложение
   вообще слушает нужный порт. Это частая настоящая причина «нет сети».
5. Качество соединений: `HOST_TCP_RETRANS` (38) и `HOST_TCP_INUSE` (37)
   в TUI не показаны, доступны в `/metrics`.

**Интерпретация.** Pulse отвечает на «трафик есть или нет», «интерфейс
сыпет ошибками или нет», «кто слушает». Проверку достижимости внешнего
адреса нужно делать обычными средствами.

**Ограничение v1 — честно.** Нет правил по сети, нет проверок доступности,
нет lane сети в Timeline (lanes — CPU, MEM, IO); пер-интерфейсные счётчики
видны в сущности и `/metrics`, но не в vitals (`docs/ROADMAP.md` 3.4, 3.9).

## 10. Большая нагрузка на память: от хоста до команды

**Симптом.** Память хоста на пределе; нужно узнать, какой контейнер и какая
команда её съели. Ручной путь — `htop`, затем `docker stats`, затем
`docker exec ps` — это четыре-пять инструментов; ниже тот же путь одним
спуском.

**Действия.**
1. `2` — Problems: цепочка давления памяти в порядке появления —
   `psi.memory` (`PSI_MEM_FULL_AVG10` 0.10/0.25), `memory.pressure`
   (`MEM_UTIL` 0.85/0.95), `swap.pressure` (0.25/0.60), при исходе
   `memory.oom`. EVIDENCE у каждой: метрика, порог, значение, сущность.
2. `1` — Overview: блок `RELEVANT LOGICAL ENTITIES` — таблица
   `NAME CPU MEM S [WHY]`: строки отранжированы, `WHY` объясняет, почему
   сущность попала в список.
3. `3` — Entities: `s` — сортировка по MEM; `m` — логический вид: сервис
   показан как `unit+14p` с памятью cgroup (процессы не удваивают сумму,
   потому что cgroup-счётчик их уже включает).
4. `Enter` на контейнер: SUMMARY — `CG_MEM_CURRENT`, `CG_MEM_LIMIT`,
   `CG_MEM_UTIL`, события `CG_MEM_EVENTS_HIGH/MAX/OOM/OOM_KILL`;
   блок CHILDREN — процессы внутри.
5. `Enter` на процесс: терминальный уровень — **пользователь, исполняемый
   файл, рабочий каталог**. Это ответ «какая команда или скрипт».
   Метрики процесса (`PROC_RSS`, `PROC_OOM_SCORE`) — при включённом
   экспорте процессов: в реестре они OptIn.
6. `4` — Timeline: lane `MEM` — когда начался рост; `A` на момент до роста,
   `B` на сейчас, `D` — semantic diff: какие сущности появились и как
   изменились метрики.

**Интерпретация.** Это направленный спуск: хост → cgroup контейнера →
процесс → команда, с evidence на каждом уровне. Ручная цепочка инструментов
заменяется одним расследованием, но вывод остаётся за оператором: Pulse
показывает, кто держит память и когда это началось, а не «кто виноват».

**Ограничение v1 — честно.** Владелец cgroup определяется по префиксу пути
(без обращения к Docker/CRI API), namespace pod — `unknown`; метрики уровня
процесса — OptIn; без прав детали чужого процесса — `restricted`.

## 11. Проблемы, метрики и журналы событий

**Симптом.** «Проблема есть — где посмотреть, что писал сервис в этот
момент».

**Честный ответ сразу.** Системные журналы Pulse не читает: коллектора
journald или syslog нет (совпадения `/var/log` в коде — только тестовые
фикстуры). Слово «события» в Pulse означает собственный журнал агента,
а не журнал системы.

**Что есть и как этим пользоваться.**
1. `2` — Problems: проблема — это событие с evidence (метрика, порог,
   значение, сущность) и моментами входа и снятия. Дребезг подавлен:
   вход после 3 тактов, снятие после 15 (по умолчанию).
2. `4` — Timeline `: story`: значимая история — появление и исчезновение
   сущностей, операционные изменения; потоки ядра вычищены семантическим
   конвейером.
3. `4` — Timeline `: raw events`: сырой поток, включая шум; режим
   вторичный по замыслу.
4. Границы журнала: `max_events` 8192 и участие в общем потолке памяти
   (64 MiB по умолчанию) — при переполнении старые события вытесняются.
5. Терминальный уровень процесса: открытые файлы — какие журналы держит
   процесс. Это мост к внешнему журналу: Pulse даёт путь, читать нужно
   снаружи.
6. Сопоставление с внешними журналами по времени: `/metrics` или
   remote_write в существующий TSDB плюс `pulse diff --from --to`
   (принимает `30s`, `5m`, `now` или UNIX-миллисекунды).

**Интерпретация.** Привязка «проблема ↔ метрика ↔ сущность ↔ время» в v1
есть и она строгая. Привязки «проблема ↔ строка журнала» нет.

**Ограничение v1 — честно.** См. `docs/ROADMAP.md` 3.7: чтение journald
стоит в очереди отдельным крупным пунктом — с бюджетом памяти и редакцией
секретов.

## 12. Таймлайн: что он показывает про прошлое

**Симптом.** «Таймлайн не позволяет увидеть картину прошлого».

**Что уже хранится.** Агент держит свою историю в памяти: hot-слой
300 тактов (около 5 минут при такте 1 c), warm-слой 360 корзин по 10 тактов
(около часа), журнал событий 8192 записи, потолок 64 MiB
(`pulse-core/src/config.rs`). Потолок сокращает глубину, а не растит RSS —
это зафиксированный выбор: короткая честная история лучше агента, который
сам стал проблемой. Фоновый режим уже есть: `pulse serve` — сбор и экспорт
без TUI.

**Действия.**
1. `4` — Timeline: rail времени, State River (наблюдённые переходы
   состояний), lanes CPU/MEM/IO по абсолютной шкале, Incident Story.
2. `←→` — scrub по времени, `+/−` — зум окна, `F` — вернуться к LIVE,
   `p` — пауза отображения.
3. `A` и `B` — метки двух моментов, `D` — semantic diff: структурные
   изменения и изменения метрик, без причинных утверждений.
4. `: story` и `: raw events` — переключение режимов.
5. `Enter` на строке — переход к сущности, которой касается изменение:
   расследование продолжается из таймлайна.

**Интерпретация.** Таймлайн отвечает на «когда началось» и «что изменилось
между двумя моментами». Он не восстанавливает то, чего нет в его истории.

**Ограничение v1 — честно.**
- глубина ограничена: около 5 минут точных тактов и около часа корзин,
  при жёстком бюджете памяти — меньше;
- история не переживает перезапуск агента: она в памяти, не на диске
  (`docs/ROADMAP.md` 3.10);
- отметок событий на самой линии нет и исторических корзин State River
  нет — оба пункта отложены (3.8);
- lanes только CPU, MEM, IO: сети и файловых систем на линии нет (3.9);
- спарклайн рисуется от двух реальных точек, иначе честно
  `collecting history`;
- анимации нет вовсе. Спецификация v0.9 нормирует её в разделе 6
  (спокойная пульсация для здорового состояния, ускоренная при росте
  активности, направленное движение для потока, рывок и возврат для
  retransmit, collapse → reform для перезапуска, короткая вспышка для
  дискретного события, замедление при ожидании) и предусматривает флаг
  `--no-animation`. В коде анимации не существует: в `crates/` нет ни
  одного совпадения по `animation`, `GlyphSurface` — статическая сетка
  классов состояния, а тест требует, чтобы две сборки одного glyph были
  побайтово равны. Реализован раздел 7 (glyph как логическая сетка,
  пресеты, ASCII-fallback), но не раздел 6.

## Чего сценарии НЕ дают (обобщённо)

- Причинных утверждений: Pulse связывает сущности и показывает evidence
  (метрика + порог + значение), но не формулирует «X вызвало Y».
- Событий вне тактов: разрешение — один такт (по умолчанию 1 c); процесс,
  умерший быстрее такта, в графе не появится.
- Прав чужих процессов: без привилегий детали fd/портов — `restricted`.
- Системных журналов: коллектора journald или syslog нет; связь с журналами
  — только через открытые файлы процесса.
- Состояния systemd unit: `active`/`failed` не читается.
- Проверок доступности сети: ping, DNS, TCP-connect отсутствуют.
- Списка точек монтирования: наружу выходят только корень и худшая
  значимая ФС.
- Истории после перезапуска агента: она хранится в памяти.
- Анимации состояния из раздела 6 спецификации: glyph статичен, флага
  `--no-animation` нет.

Каждое ограничение из этого списка имеет решение: механизм, стоимость
и критерий приёмки — в `docs/SOLUTIONS.md` (нумерация решений совпадает
с номерами сценариев: решение 1 — порт, 2 — сервис, 3 — сеть, 4 — память,
5 — журналы, 6 — таймлайн, 7 — показания). Статус и очередь работ —
в `docs/ROADMAP.md` (раздел 3, порядок волн — раздел 8).
