# SOLUTIONS

Решения по шести сценариям оператора и трём вопросам о показаниях. Формат
каждого пункта: решение → механизм → инженерный ход, снимающий риск → что
видит оператор → приёмка. Ограничения здесь не обсуждаются: они разобраны
в `docs/FEATURES.md` и `docs/ROADMAP.md`, этот документ отвечает на «как
сделать».

Правило документа: решение считается пригодным, только если названы
источник данных, стоимость за такт и проверяемый критерий приёмки.

---

## 1. Порт занят: ответ за одно нажатие

**Решение.** Ввести сущность `Socket` **только для слушающих сокетов**
и обратный индекс `inode → pid`. Команда палитры `: port 8080` открывает
Inspector владельца порта.

**Механизм.** Половина решения уже написана — её нужно только развернуть
в другую сторону:
1. `parse_net_sockets` (`pulse-collect/src/details.rs:194-228`) уже читает
   `/proc/net/tcp`, `tcp6`, `udp`, `udp6` и **уже оставляет только
   слушающие сокеты**: состояние `0A` для TCP, нулевой удалённый адрес
   для UDP. Отбор, который снимает возражение о мощности графа, существует
   в коде.
2. `read_descriptors` (`details.rs:84-127`) уже извлекает inode из целей
   вида `socket:[555001]`, а `listening_ports` (`details.rs:148-166`)
   сопоставляет их с таблицей. Сейчас направление одно: процесс → порты.
   Нужен обратный индекс: один проход по `/proc/*/fd` строит `inode → pid`,
   и тогда таблица сокетов получает владельца.
3. Сущность `Socket { proto, addr, port }` связывается с процессом связью
   владения; процесс уже связан с cgroup, cgroup — с unit или контейнером,
   поэтому цепочка «порт → процесс → контейнер → сервис» получается
   бесплатно из существующего графа.
4. Источник данных остаётся абстрактным: чтение идёт через `FsSource`
   (`details.rs`), поэтому тест на фикстуре `/proc` пишется без реального
   хоста — фикстуры такого вида в файле уже есть.

**Инженерный ход, снимающий риск.** Возражение против сущности `Socket`
в `IDEAS.md` — мощность графа: тысячи соединений против десятков процессов.
Ход: в граф попадают **только слушающие** сокеты. Их на хосте десятки,
а не тысячи; ESTABLISHED-соединения остаются деталью процесса по
требованию, как сейчас. Риск исчезает, а вопрос «кто занял порт»
закрывается полностью.

**Что видит оператор.**
- `: port 8080` → Inspector сокета: владелец (pid, exe, user, cwd),
  контейнер или unit выше по владению, время появления сокета;
- в Entities — фильтр `f` по типу socket: список слушающих портов хоста;
- в Inspector процесса секция LISTENING остаётся как есть.

**Приёмка.**
- на стенде с занятым портом `: port 8080` даёт pid, исполняемый файл
  и владельца за один такт;
- число сущностей socket в снимке равно числу строк LISTEN в `/proc/net/*`
  (тест на фикстуре `/proc`);
- без прав ответ — `restricted` с указанием, какого доступа не хватает,
  а не пустой список;
- `pulse scorecard`: прирост `store_bytes` не более чем на число слушающих
  сокетов, помноженное на размер записи сущности.

## 2. Сервис не запускается: причина смерти вместо тишины

**Решение.** Два независимых источника: (а) редкий опрос списка неудачных
unit — даёт проблему `unit.failed`; (б) детали unit по требованию — дают
код выхода и число перезапусков.

**Механизм.**
1. Раз в 30 секунд (не каждый такт) выполняется один вызов
   `systemctl list-units --state=failed --no-legend --plain`. Для каждой
   строки создаётся сущность unit, даже если у неё больше нет cgroup, —
   именно поэтому упавший сервис перестаёт быть невидимым.
2. Правило `unit.failed`: наличие unit в этом списке → проблема класса
   crit без гистерезиса по тактам (состояние дискретное, дребезга нет).
3. При открытии unit в Inspector — детали по требованию, тем же
   механизмом однотактного кэша, что и порты с дескрипторами:
   `systemctl show -p ActiveState,SubState,Result,ExecMainStatus,NRestarts,InvocationID`.
   `Result` даёт язык причины: `exit-code`, `oom-kill`, `timeout`,
   `signal`, `core-dump`.
4. Рост `NRestarts` между опросами превращается в событие «сервис
   перезапускается» и попадает в Story.

**Инженерный ход, снимающий риск.** Отказ от D-Bus и от подписки на
`PropertiesChanged`: они дают зависимость и постоянный поток событий.
Здесь стоимость ограничена сверху — один внешний вызов в 30 секунд плюс
вызов по требованию только для открытой сущности. Опрос выключается
конфигурацией, а отсутствие systemd на хосте — не ошибка, а пустой
источник.

**Новое для проекта — и как это удержать.** Сегодня агент не запускает
внешних процессов: поиск `process::Command` по `pulse-collect`,
`pulse-store` и `pulse-cli` не даёт ни одного совпадения. Решения 2 и 5 —
первый такой случай, поэтому запуск обязан быть заперт по образцу уже
существующей абстракции чтения: как файловый доступ идёт через
`FsSource`, так вызов внешней команды идёт через один трейт-источник
с таймаутом, лимитом вывода и подменой в тестах на фикстуру. Тогда
в тестах не появляется зависимость от systemd, а в конфигурации остаётся
один выключатель. Образец такого запирания в проекте уже есть:
`pulse-collect/src/actions.rs` — единственное место, где Pulse меняет
состояние системы (отправка сигналов через rustix), и оно защищено двумя
условиями: проверкой совпадения времени старта процесса и обязательным
`security.allow_actions`, выключенным по умолчанию. Внешние команды
решений 2 и 5 обязаны получить такой же выключатель и такой же короткий
белый список: только `systemctl` с перечисленными свойствами и только
`journalctl` с ограничением по строкам и времени. Если трейт-источник
и выключатель не вводить, стоимость расползётся по коллекторам —
этого допускать нельзя.

**Что видит оператор.**
- Problems: `unit.failed` со строкой причины (`Result=oom-kill` читается
  сразу, без похода в журнал);
- Inspector unit: `ActiveState`, `SubState`, код выхода, число
  перезапусков;
- Story: «unit перезапущен N раз за окно».

**Приёмка.**
- остановленный командой `systemctl stop` сервис не даёт ложной проблемы
  (он `inactive`, а не `failed`);
- упавший сервис появляется в Problems не позже 30 секунд;
- `Result=oom-kill` совпадает с событием `memory.oom` того же окна —
  две независимые улики об одном факте;
- стоимость: `scripts/measure-cost.sh` показывает прирост CPU-цикла такта
  в пределах шума, потому что опрос вне такта.

## 3. Нет сети и нет интернета: разделить два разных ответа

**Решение.** Пассивные правила по интерфейсу отвечают на «сеть на хосте
сломана»; опциональный локальный пробник отвечает на «цель недоступна».
Оба ответа существуют раздельно, и это главное.

**Механизм.**
1. Новая дешёвая метрика `NETIF_OPERSTATE` из `/sys/class/net/*/operstate`
   (одно чтение на интерфейс) и правило `netif.down`: интерфейс, который
   был `up` и стал `down`, — crit.
2. Правила `netif.errors` и `netif.drops` на долю от пакетов с гейтом
   «минимум пакетов в секунду», по образцу гейта `has_disk_traffic`:
   на тихом интерфейсе доля не считается.
3. Метрика темпа retransmit: отношение приращения retransmit
   к приращению отправленных сегментов (`/proc/net/snmp`), правило —
   на долю, не на абсолютное число.
4. Пробник: секция конфигурации `probe`, **выключенная по умолчанию**,
   со списком целей (`host:port`), интервалом и таймаутом. Метод —
   TCP-connect, метрики состояния и задержки цели, правило `probe.down`.
5. Lane `NET` на Timeline и отметка события `netif.down` на линии.

**Куда встают новые метрики (проверено по реестру).** Host-диапазон
`1..=49` занят полностью, поэтому новые номера берутся из сетевого блока
`70..=89`, где заняты только `70..=79` (`pulse-core/src/metric.rs:244-254`):
operstate, темп retransmit и две метрики пробника — `80`, `81`, `82`, `83`.

**Форма правил уже готова.** Новое правило — это заполнение существующей
структуры `ThresholdRule` (`pulse-engine/src/rules.rs:119-142`): метрика
по видам сущностей (`host_metric`, `owner_metric`, `device_metric`),
пороги функцией из конфигурации (`thresholds: fn(&RulesCfg) -> (f64, f64,
f64)`), предусловие `gate: Option<fn(&RuleCtx, EntityId) -> bool>`.
Новый гейт «минимум пакетов» пишется по образцу `has_disk_traffic`
(`rules.rs:199`) и `has_cpu_quota` (`rules.rs:485`), список правил —
`default_rules()` (`rules.rs:415`).

**Инженерный ход, снимающий риск.** Активная проверка противоречит
принципу «Pulse — наблюдатель». Ход: пробник не является коллектором
по умолчанию, цели задаёт только оператор, и он отвечает исключительно
за различение «линк жив, но цель недоступна». Наблюдатель остаётся
наблюдателем; пробник — явно включаемый инструмент, который оператор
включает, когда ему нужен именно этот ответ.

**Что видит оператор.**
- выдернутый кабель или сброшенный интерфейс — `netif.down` в Problems
  с указанием интерфейса;
- деградация линии — `netif.errors` или `tcp.retrans.rate`;
- при включённом пробнике — `probe.down` при живых интерфейсах: это и есть
  «сеть есть, интернета нет»;
- на Timeline видно, что было раньше: падение интерфейса или падение цели.

**Приёмка.**
- `ip link set <if> down` на стенде → `netif.down` в течение трёх тактов;
- блокировка цели файрволом при живом линке → `probe.down`, при этом
  `netif.down` не срабатывает;
- на тихом интерфейсе (ноль пакетов) правила errors и drops не срабатывают
  — тест на гейт;
- при выключенном пробнике ни одного сетевого соединения агент не
  открывает (тест: нет исходящих connect).

## 4. Нагрузка на память: ответ приходит вместе с проблемой

**Решение.** Проблема класса памяти несёт готовый спуск: три cgroup
с наибольшим вкладом и внутри каждой — процесс с наибольшим RSS вместе
с его командой. Оператор не ищет виновника, он его читает.

**Механизм.**
1. При формировании проблемы `memory.pressure`, `psi.memory`
   или `memory.oom` анализатор (`pulse-engine/src/analyzer.rs`) сам
   ранжирует cgroup-сущности по метрике `CG_MEM_CURRENT` из текущего
   снимка и берёт три верхние. Существующее ранжирование строк
   (`pulse-tui/src/fold.rs`, взвешенная сумма причин) для этого
   не используется: оно живёт в слое интерфейса и работает на `LogicalRow`,
   поэтому движок не может и не должен его вызывать. Разделение
   сохраняется: интерфейс ранжирует строки для оператора, движок
   ранжирует участников проблемы по одной явной метрике.
2. Строки-участники добавляются через **существующий хук**
   `extra: Option<fn(&RuleCtx, EntityId) -> Vec<Evidence>>`
   (`pulse-engine/src/rules.rs:141`, «дополнительные доказательства») —
   новой машинерии для самих строк не нужно.
3. Чтобы строка была навигабельной, тип доказательства придётся
   расширить: сейчас `Evidence` — это только `label`, `value`,
   `threshold: Option<String>` (`pulse-core/src/problem.rs:41-48`),
   ссылки на сущность в нём нет (сущность есть у самой проблемы,
   `problem.rs:87`). Нужно добавить `entity: Option<EntityId>` —
   изменение маленькое и локальное, но без него `Enter` на участнике
   некуда вести.
4. Внутри выбранной cgroup показывается процесс с максимальным RSS
   и его командная строка — данные терминального уровня, который уже
   реализован.
5. `PROC_RSS` и `PROC_OOM_SCORE` собираются **для top-N процессов по RSS**
   (N настраивается, по умолчанию 20), а не для всех и не только по
   явному включению.

**Инженерный ход, снимающий риск.** Метрики процессов сейчас OptIn из-за
cardinality: на хосте сотни процессов. Ход — top-N по RSS: 20 записей
вместо 500, при этом именно те, которые нужны в инциденте памяти.
Остальные процессы остаются сущностями графа без временных рядов.

**Что видит оператор.** Открыл Problems — в проблеме памяти сразу три
контейнера с долями и команда главного пожирателя. Ручная цепочка
`htop` → `docker stats` → `docker exec ps` сокращается до одного экрана,
а спуск остаётся доступным для проверки.

**Приёмка.**
- на стенде с контейнером-пожирателем проблема памяти содержит его имя
  и команду процесса; число действий оператора — одно;
- сумма долей участников не превышает 100% (тест на арифметику вклада);
- число серий процессов в снимке не больше N (тест на потолок);
- `pulse scorecard`: `series_live` растёт не более чем на N × число
  метрик процесса.

## 5. Журналы: привязка без хранения журналов

**Решение.** Pulse не хранит логи и не становится хранилищем. Он читает
**хвост журнала по требованию за окно проблемы** и показывает его как
evidence.

**Механизм.**
1. У проблемы уже есть моменты входа и снятия. Это и есть готовый ключ
   запроса: окно `[enter, now]`.
2. При открытии проблемы или сущности unit оператор запрашивает секцию
   JOURNAL. Выполняется одно ограниченное чтение:
   `journalctl -u <unit> --since <enter> --until <now> -n 50 -o short-iso
   --no-pager` с таймаутом. Для процессов, у которых в деталях видны
   открытые файлы журналов, альтернативный источник — хвост этого файла
   ограниченного размера.
3. Прочитанные строки проходят через существующий механизм редакции
   секретов (счётчик редакций уже есть в реестре метрик) и **не попадают
   в store**: они живут ровно один такт в кэше деталей.
4. На Timeline: при выбранном окне `A`/`B` тот же запрос выполняется
   для окна сравнения — журнал читается за интервал, а не «весь».

**Инженерный ход, снимающий риск.** Возражение против логов — объём
и бюджет памяти. Ход: журнал никогда не входит в историю. Хранится только
время проблемы, а текст извлекается в момент запроса и выбрасывается.
Поэтому «привязка проблемы к журналу» получается без роста `store_bytes`
и без изменения потолка памяти.

**Что видит оператор.** Из проблемы `unit.failed` две клавиши до пятидесяти
строк журнала именно этого unit именно за окно проблемы. Из процесса —
хвост того файла, который он держит открытым.

**Приёмка.**
- `store_bytes` до и после открытия секции JOURNAL не меняется
  (`pulse scorecard`);
- запрос ограничен по времени и по числу строк: тест на таймаут
  и на лимит;
- секреты в строках заменены, счётчик редакций вырос;
- если `journalctl` отсутствует или недоступен, секция говорит `restricted`
  с причиной, а не исчезает.

## 6. Таймлайн: прошлое, отметки и живой кадр

Три независимых решения; каждое ценно само по себе.

### 6.1 Отметки событий на линии

**Решение.** Биннинг событий окна по колонкам rail: одна колонка —
интервал `zoom_ms / ширина`. В колонке рисуется глиф самого значимого
события интервала; глифы по классам событий уже определены в ядре.

**Механизм.** События окна уже в снимке, скраб курсором уже есть.
Добавляется раскладка «событие → колонка» и выбор победителя колонки
по классу. При скрабе на колонку Story прокручивается к её событиям —
связь линии и текста становится двусторонней.

**Приёмка.** Событие, произошедшее в момент T, отображается в колонке,
содержащей T, при любом зуме (тест на границы интервалов); при пустом
окне линия остаётся пустой, а не рисует ложные отметки.

### 6.2 Прошлое переживает перезапуск

**Решение.** Сброс warm-слоя в один файл и загрузка при старте.

**Механизм.** Warm-слой — это готовые корзины фиксированного размера
(`pulse-store/src/warm.rs`, вытеснение и учёт объёма —
`pulse-store/src/lib.rs:116-218`). Запись выполняется при штатной
остановке (ограниченный shutdown по сигналу уже реализован) и раз
в 60 секунд, в один файл `/var/lib/pulse/warm.bin`, размер которого
ограничен тем же потолком, что и память. При старте файл читается;
при несовпадении версии формата или повреждении — старт с пустой
историей и событие в журнал агента (поведение fail-open).

**Формат: два варианта с честной ценой.** В `pulse-store` типы истории
не выводят serde (поиск `Serialize`/`Deserialize` по `pulse-store/src` —
ноль совпадений), а сам крейт зависит только от `pulse-core` и `tracing`
(`crates/pulse-store/Cargo.toml:10-12`). При этом serde уже есть
в workspace и используется ядром (`crates/pulse-core/Cargo.toml:11`),
поэтому речь не о новой внешней зависимости, а о новом ребре зависимости
у самого горячего крейта.

- **Вариант A (рекомендуемый):** добавить `serde = { workspace = true }`
  в `pulse-store` и вывести derive на типах корзины. Дешевле в коде,
  формат меняется вместе со структурой, совместимость держится словом
  версии в заголовке файла.
- **Вариант B:** собственная запись фиксированной раскладки (слово версии,
  число корзин, поля в фиксированном порядке). Ноль новых рёбер
  зависимостей и полный контроль над раскладкой; цена — формат нужно
  править руками при каждом изменении корзины.

Выбор между A и B — решение владельца; оба варианта требуют слова версии
и поведения fail-open при несовпадении.

**Каталог данных придётся добавить.** В секции `store` сейчас ровно семь
полей — `hot_ticks`, `warm_buckets`, `warm_bucket_ticks`, `max_events`,
`max_entity_records`, `max_series`, `max_bytes`
(`pulse-core/src/config.rs:85-105`); поля для пути на диске нет вовсе.
Значит решение вводит новое поле (например `store.data_dir`), пустое
по умолчанию: пустое значение — персистентность выключена, и текущее
поведение сохраняется без изменений. Валидация ложится туда же, где уже
проверяются интервал и глубина кольца (`config.rs:315`; существующие
ошибки — `ConfigError::Interval`, `HotTicks`, `Threshold`, `Hysteresis`).

**Инженерный ход, снимающий риск.** Диск — новая ответственность, поэтому
она сведена к минимуму: один файл, без ротации, без индексов, без
инкрементальной записи. Потеря файла не влияет на работу агента, а его
размер не может превысить уже принятый потолок.

**Приёмка.** Перезапуск агента: окно Timeline после старта содержит
корзины до остановки; повреждённый файл не мешает старту (тест на битый
файл); `store_bytes` после загрузки не превышает `max_bytes`.

### 6.3 Кадр становится живым, а бюджет остаётся прежним

**Решение.** Реализовать раздел 6 спецификации как фазу кадра
у существующей статической сетки glyph — и только у glyph.

**Механизм.**
1. В ячейку сетки добавляется фаза; поверхность строится функцией
   «сетка при фазе p», а текущая функция становится частным случаем
   `p = 0`. Детерминизм тестов сохраняется: тесты фиксируют фазу.
2. Семантика берётся из спецификации дословно: спокойная слабая пульсация
   — здоровое живое состояние, ускоренная — рост активности, направленное
   движение — поток, рывок с возвратом — retransmit, `collapse → reform`
   — перезапуск, короткая вспышка — дискретное событие, замедление почти
   до остановки — ожидание.
3. Частота перерисовки: по такту в спокойном состоянии; учащённый кадр
   только при наличии crit-проблемы и только для области glyph.
4. Флаг `--no-animation`, автоматическое отключение при не-TTY
   и при терминале без поддержки цвета.

**Инженерный ход, снимающий риск.** Анимация обычно означает перерисовку
всего экрана по кадру. Здесь фаза меняется только в области глифа —
десятки ячеек, а не весь экран; остальные блоки перерисовываются по такту,
как сейчас. Поэтому «красивее» не оплачивается ни бюджетом CPU агента,
ни детерминизмом тестов.

**Приёмка.** При `--no-animation` вывод побайтово совпадает с текущим;
фаза меняет только область glyph (тест на диффе кадров); прирост CPU
агента при активной анимации измерен `scripts/measure-cost.sh` и укладывается
в заранее заданный бюджет; в не-TTY анимация выключена автоматически.

## 7. Три вопроса о показаниях

### 7.1 Заполненность файловой системы становится проблемой

**Решение.** Правило порога плюс правило скорости: `fs.fill`
(порог заполненности) и `fs.fill.trend` (времени до заполнения меньше
заданного).

**Механизм.** Порог — обычное правило на `FS_ROOT_UTIL` и `FS_WORST_UTIL`
с гистерезисом, как у остальных восьми. Тренд считается по warm-слою:
наклон на окне и оценка времени до 100%; правило срабатывает только при
монотонном росте на окне — это гейт против ложных срабатываний
от кэшей и тонких томов.

**Приёмка.** Заполнение тестового тома до порога даёт проблему;
пилообразная запись и удаление (кэш) проблему тренда не даёт; отключение
правила конфигурацией возвращает текущее поведение.

### 7.2 Заполненность дисков подробно

**Решение.** Секция FILESYSTEMS в Inspector сущности host: точка
монтирования, тип, всего, свободно, заполненность — по всем значимым
mount, которые коллектор уже отбирает.

**Механизм.** Отбор значимых mount существует; решение публикует список
наружу. В экспорт метрики уходят с гейтом: только mount крупнее заданного
размера или заполненные выше заданной доли — так список в интерфейсе
остаётся полным, а число серий не растёт.

**Номера метрик уже есть куда положить.** Файловые системы по принятому
соглашению живут в хвосте блока дисков (`pulse-core/src/metric.rs:238-242`:
«у них та же природа, но область действия — хост»), где заняты `66..=68`,
а `63`, `64`, `65` и `69` свободны. Этого ровно хватает на три метрики
точки монтирования — размер, свободно, заполненность — с меткой mount
и одним запасным номером. Секция интерфейса рисуется помощником
заголовков `section()` (`pulse-tui/src/screens/mod.rs:340`), формат
величин берётся у строки vitals (`mod.rs:380`).

**Приёмка.** Все значимые mount видны в интерфейсе; число экспортируемых
серий равно числу mount, прошедших гейт; чтение `/proc/mounts` остаётся
одним ограниченным чтением за такт.

### 7.3 Load average

**Решение.** Показать в секции SUMMARY сущности host три значения,
нормированные на число ядер, с явной подписью нормировки. Правила
по loadavg не вводить.

**Механизм.** Метрики уже собираются; `HOST_CPU_COUNT` уже есть.
Строка vitals не расширяется: она занята показателями, которые точнее.

**Приёмка.** На хосте с известным числом ядер значение совпадает
с `uptime`, делённым на ядра; ни одно правило на loadavg не появилось.

## 8. Пайп расследования и графы

**Решение.** Главный вид — **пайп расследования**: оператор выбрал
сущность, вправо раскрылись факты о ней — откуда запущена (`exe`, `user`,
`cwd`), какой порт слушает, в каком контейнере и unit живёт, какие лимиты
и троттлинг, какие файлы держит, хвост её лога, системный журнал про неё,
её проблемы. Это не топологический граф: глубина ровно два уровня
(категория → строки), пересечений нет по построению, `→` раскрывает
ветку, `←` сворачивает, `Enter` по ветке владельца продолжает
расследование по уже принятому правилу уровней.

**Два режима одного содержимого.** Пайп с отступами укладывается в 80
колонок; граф-режим боксами (клавиша `g`) требует замеренных **100
колонок и 25 строк** — бокс 22 колонки, три бокса в ряду, ярус
переносится на следующий ряд. Ниже порога вид меняется автоматически
и с подписью: молча подменять раскладку нельзя. Свёрнутая ветка — бокс
в две строки с `▸` и **без единого чтения источника**; раскрытие делает
одно чтение и кладёт в кэш снимка, а ширина бокса фиксирована, поэтому
кадр растёт только вниз.

**Почти всё уже собрано.** `ProcessDetails` даёт `user`, `exe`, `cwd`,
`fd_total`, `files`, `ports` и отдельный признак `restricted`
(`pulse-core/src/details.rs:46-62`), читается по требованию с кэшем
на снимок (`DetailsCache`, `details.rs:92`). Владелец, лимиты, проблемы
и ресурсы берутся из графа и реестра метрик. Не обеспечены данными
только две ветки: `log` и `journal` — они появляются вместе с решением 5.

**Два вспомогательных вида отделены сознательно.** Дерево подпроцессов
требует ребра процесс → процесс: `ppid` разбирается
(`pulse-collect/src/parse.rs:201`, `:240`), но `process.rs:279-281`
ставит только `RunsIn` на cgroup — пока ребра нет, дерево строить не
из чего. Граф владения с fan-in (200 процессов → одна cgroup → один unit)
— настоящий DAG, ему нужна слоистая раскладка, и он самый дорогой.

Полный проект (алгоритм раскладки, таблицы глифов и стилей рёбер, бюджет
кадра, деградация вида, клавиши, критерии приёмки) — `docs/GRAPH-VIEW.md`.

природу агента, и его стоит вводить, когда всё пассивное уже сделано.
